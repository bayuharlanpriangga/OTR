## Current Architecture
- Vanilla HTML/CSS/JS, ES Modules, tanpa framework/build step.
- Routing: hash-based (`#/reading`, dst), didaftarkan di `js/app.js` via `registerRoute()`.
- State: satu object global di `js/core/state.js`, diakses via `getState()`/`setState()`/`patchState()`.
- Komunikasi antar modul lewat `js/core/event-bus.js` (event: `route:change`, `toast:show`, `state:change`).
- Halaman = modul dengan `export default { render(container, params) }`, di-load lazy lewat dynamic `import()`.
- Data domain tarot independen dari UI (`data/`), dikonsumsi Tarot Engine (`js/tarot/`) tanpa DOM sama sekali.
- **Tarot Engine (`js/tarot/`) juga independen dari state management/UI** — `tarot-engine.js` tidak meng-import `js/core/state.js` atau `event-bus.js`. Layer di atasnya (`js/pages/reading.js`, Phase 5) yang menyambungkan hasil `engine.getReading()` ke `patchState("reading", ...)`. Keputusan ini menjaga engine tetap testable murni lewat `node` tanpa DOM/browser — terbukti berguna waktu memverifikasi bugfix lokasi folder di awal Phase 5 (lihat Known Issues).
- `js/tarot/` sekarang benar-benar berada di `js/tarot/` (dipindah dari root repo di awal Phase 5 — lihat Completed & Known Issues), sesuai Master Spec §3.
- **`js/tarot/interpretation.js` (Phase 6) mengikuti pola independensi yang sama** — fungsi murni, tidak import `state.js`/`event-bus.js`, tidak tahu apa itu `TarotEngine`. Dipanggil langsung oleh page controller (`reading.js` & `result.js`), sejajar dengan `tarot-engine.js` — bukan lapisan di atas/di bawahnya. `TarotEngine` menangani *fisik* reading (deck, draw, status), `interpretation.js` menangani *makna* dari kartu yang sudah ditarik; keduanya tidak saling import.
- Struktur folder & nama file mengikuti Master Spec §3 persis.

## Important Decisions
- Router pakai hash (`#/...`), bukan History API — supaya kompatibel static hosting tanpa rewrite rule.
- Font: Fraunces (display) + Public Sans (body) + IBM Plex Mono (data/angka) via Google Fonts CDN.
- Palet warna "night-reading table": obsidian/plum sebagai ruang, gold sebagai foil-accent, oxblood untuk state reversed/destructive.
- Data Minor Arcana (56 kartu) di-generate dari kombinasi tema suit × tema rank/court, bukan ditulis satu-satu manual. Teks Major Arcana (22 kartu) ditulis individual.
- `tarot-keywords.js` sengaja dipisah dari `tarot-cards.js` supaya fitur search/filter (Phase 9) & quiz (Phase 21) bisa jalan tanpa nge-load seluruh teks upright/reversed 78 kartu.
- `image` path memakai format `/assets/images/tarot/{suit-or-major}/{slug}.webp` — placeholder, asetnya diisi di Phase 4.
- **Randomization pakai `crypto.getRandomValues()` dengan rejection sampling** (bukan modulo langsung) supaya distribusi shuffle/orientation tidak bias ke angka kecil — sesuai Master Spec §10. Fallback ke `Math.random()` hanya kalau Web Crypto API benar-benar tidak tersedia di environment.
- **`TarotEngine` sengaja dipisah dari `TarotDeck`**: `deck.js` cuma tahu soal kartu fisik (draw/shuffle/reset), tidak tahu apa itu "reading" atau "spread". `tarot-engine.js` yang mengorkestrasi deck + orientation + spread jadi satu reading entity. Pemisahan ini supaya tiap modul gampang dites sendiri-sendiri (lihat runtime test Phase 3).
- **Reveal dipisah jadi state tersendiri dari draw** (`drawing` → `revealing` → `interpreting`), bukan digabung jadi satu langkah — mengikuti state machine Master Spec §15 dan mencegah UI (Phase 5) "skip" langsung dari draw ke interpretasi tanpa render animasi reveal.
- **`drawCard()` mengembalikan objek kartu penuh** (`card`, hasil resolve dari `getCardById`), tapi yang disimpan permanen ke `reading.cards` hanya `{ positionId, cardId, orientation }` — konsisten dengan schema Reading Entity Master Spec §14 (tidak menyimpan data kartu yang sudah redundan dengan `data/tarot-cards.js`).
- **`js/components/tarot-card.js` sengaja tidak tahu apa-apa soal `TarotEngine`** — komponen cuma nerima props data kartu + flag state. Pemisahan ini konsisten dengan pola yang sudah dipakai di Phase 2 & 3 (data/logic independen dari UI): Phase 5 nanti yang jadi "lem" antara `engine.drawCard()` dan `renderTarotCard()`.
- **Reversed orientation memutar seluruh wajah kartu 180°** (bukan cuma teks atau cuma artwork) — meniru tampilan kartu tarot fisik yang benar-benar terbalik, bukan sekadar ikon "reversed" di kartu yang tetap tegak. Badge kecil di pojok (tidak ikut rotasi) yang menjaga keterbacaan status orientasi.
- **Background art kartu pakai CSS `background-image` di sebuah `<div>`, bukan `<img>`** — karena `image` path di `data/tarot-cards.js` masih placeholder (aset `.webp` belum ada, lihat Known Issues Phase 2/3). Dengan `background-image`, gambar yang gagal load tidak memunculkan broken-image icon; huruf awal nama kartu (`.tarot-card__art-fallback`) selalu jadi fallback yang terlihat sengaja, bukan rusak. Begitu aset asli tersedia, tidak perlu ubah komponen — tinggal isi file di path yang sudah direferensikan.
- **`js/pages/reading.js` sengaja membuat `TarotEngine` baru tiap kali `render()` dipanggil** (bukan singleton module-level yang dipertahankan lintas navigasi) — navigasi ke `#/reading` = mulai reading baru, konsisten dengan mental model "reading" sebagai sesi sekali jalan. State reading yang **sudah selesai** dipertahankan lewat `js/core/state.js` (bukan lewat instance engine), supaya Result Page bisa dibaca ulang tanpa bergantung ke module reading.js.
- **Kategori interpretasi (general/love/career/spiritual) dipilih di step Pertanyaan, bukan otomatis dari spread** — walau tiap spread punya `category` default (dipakai sebagai nilai awal `<select>`), user tetap bisa override. Diteruskan apa adanya ke `interpretCard()`/`synthesizeReading()` (Phase 6) sebagai parameter `category`.
- **(Supersedes catatan Phase 5)** Result Page sekarang benar-benar memakai `synthesizeReading()` untuk "Overall Theme/Key Message/Reflection" — bukan lagi ringkasan sementara. Disclaimer "Interpretation Engine penuh menyusul di Phase 6" sudah dihapus dari UI karena sudah tidak akurat.
- **"Simpan Reading" dan "Tulis Journal" di Result Page dibuat `disabled` dengan `title` yang menyebutkan fase aktivasinya** (Phase 8, Phase 11) — bukan disembunyikan begitu saja — supaya user tahu fitur itu memang direncanakan, bukan lupa dikerjakan.
- **Form Pertanyaan/Niat/Kategori dibaca lewat `FormData(form)`**, bukan `form.<name>.value` — lebih eksplisit, dan (efek samping yang disengaja dimanfaatkan) membuat halaman ini testable lewat `jsdom` tanpa workaround.
- **Prioritas makna Master Spec §22 diimplementasikan penuh 4 tier walau tier 1 ("position-specific") saat ini tidak pernah punya data untuk dipakai** — pilihan sadar, bukan disederhanakan jadi 3 tier. Alasannya: (a) tetap sesuai kontrak spec apa adanya, (b) jadi titik ekstensi nyata kalau suatu saat ada kebutuhan makna per-posisi yang authored (mis. "The Fool di posisi Future" beda dari "The Fool di posisi Past"), dan (c) diuji eksplisit di runtime test Phase 6 supaya perilaku fallback-nya terverifikasi, bukan cuma diasumsikan.
- **`reflection` (field baru di output `interpretCard`) dipilih dari bank template lewat hash string deterministik, bukan `Math.random()`** — konsekuensinya: reflection prompt yang sama akan selalu muncul untuk kombinasi kartu+posisi+orientasi yang sama. Ini trade-off yang disengaja: engine yang benar-benar deterministik (gampang dites, hasilnya reproducible) lebih penting untuk MVP daripada variasi teks yang terasa "hidup" tapi tidak predictable — variasi lewat randomness asli bisa ditambahkan nanti kalau dianggap perlu, tanpa mengubah kontrak fungsi.
- **`synthesizeReading()`'s `keyMessage` = advice dari kartu di posisi TERAKHIR**, bukan gabungan semua advice atau pemilihan berbasis makna semantik — heuristik paling sederhana yang tetap masuk akal untuk spread naratif linear yang ada sekarang (past→present→future, situation→obstacle→advice, dst., di mana posisi terakhir umumnya paling actionable). Didokumentasikan sebagai heuristik yang mungkin perlu direvisi kalau spread non-linear (mis. Mind/Body/Spirit yang tidak punya urutan naratif jelas) ditambahkan nanti.
- **`js/pages/reading.js` dan `js/pages/result.js` masing-masing memanggil `interpretCard()`/`synthesizeReading()` sendiri-sendiri saat render**, tidak saling berbagi hasil lewat state — `reading.js` memakai hasilnya untuk tampilan sementara (panel per kartu) dan untuk `reading.summary` (`synthesis.theme`, satu string, sesuai schema Master Spec §14); `result.js` menghitung ulang dari `reading.cards`/`spreadId`/`category` yang tersimpan. Konsisten dengan pola "page membaca id lalu resolve data" yang sudah dipakai sejak Phase 5 — dan karena `interpretCard`/`synthesizeReading` murni & cepat (bukan network call), menghitung ulang jauh lebih sederhana daripada menyinkronkan cache hasil lewat state.

## Known Issues
- **Masih belum diuji di browser sungguhan** (sandbox tidak punya headless browser) — Phase 3 divalidasi lewat `node --check` + runtime test Node; Phase 4–6 divalidasi lewat `node --check` + runtime test `jsdom` (struktur DOM, atribut, event handler, full user flow Reading→Result dengan interpretasi sungguhan). Tapi visual asli (flip 3D, gradient, font Fraunces/Public Sans, animasi shuffle, layout responsive di breakpoint sungguhan) **belum pernah dilihat langsung** — rekomendasi kuat sebelum lanjut lebih jauh: smoke test manual di browser nyata (buka `#/reading`, jalankan satu reading penuh sampai `#/result`).
- Path gambar kartu (`image`) menunjuk ke file `.webp` yang belum ada secara fisik — `tarot-card.js` sudah didesain graceful (lihat "Important Decisions"), tapi aset sungguhan tetap belum ada; belum ada phase khusus yang secara eksplisit menjadwalkan pembuatan asetnya.
- Teks upright/reversed Minor Arcana bersifat templated — cukup untuk fungsi MVP, bisa diperkaya nanti tanpa perubahan struktur.
- Belum ada `manifest.json` / `favicon.ico` (baru dibutuhkan di Phase 24 — PWA).
- Fitur "matikan kartu terbalik" (custom `reversedProbability`) sudah didukung API-nya di `orientation.js`/`tarot-engine.js`, dan `createReading()` di `reading.js` **belum** meneruskan opsi ini (masih pakai default 50/50) karena UI Settings untuk mengaturnya belum ada — placeholder untuk phase UI Settings nanti.
- **Reading yang sedang berjalan (belum `completed`) hilang kalau user menutup tab/reload** — belum ada persistence sama sekali (disengaja, itu scope Phase 8 — Local Storage). `abortReading()` dipanggil kalau user membatalkan lewat UI, tapi tidak ada penanganan untuk unload/reload browser di tengah reading.
- **Result Page hanya bisa menampilkan reading yang baru saja selesai di sesi browser yang sama** (dibaca dari `js/core/state.js`, bukan dari storage) — refresh halaman `#/result` akan kehilangan datanya dan menampilkan empty state. Ini juga scope Phase 8.
- **Five Card spreads** (`career_path`, `love_reading`) sudah ada lengkap di `data/default-spreads.js` sejak Phase 2 tapi belum dimunculkan sebagai opsi di Reading Setup — Roadmap Phase 5 eksplisit cuma minta One Card & Three Card; kemungkinan masuk penyempurnaan Reading experience di fase berikutnya, atau perlu diklarifikasi apakah termasuk salah satu fase yang sudah ada atau butuh entri roadmap sendiri.
- Bugfix folder `tarot/` → `js/tarot/` (lihat Completed Phase 5) sempat lolos tanpa ketahuan sepanjang Phase 3–4 karena validasi kedua phase itu memanggil modul lewat path absolut manual di script test, bukan lewat resolusi import relatif seperti yang akan dipakai browser sungguhan — dicatat di sini sebagai pengingat: validasi `node --check` + runtime test dengan import manual **tidak** menjamin struktur folder benar, cuma menjamin syntax & logic modul itu sendiri benar.
- **Bug ditemukan & diperbaiki selama Phase 6 (sebelum sempat terkirim), dicatat sebagai pengingat proses:** draft pertama `result.js` memanggil `synthesizeReading({ entries: [...] })` dengan `entries` berbentuk `{ entry, position, card }` (mengikuti struktur internal `result.js` sendiri), padahal `synthesizeReading()` mengharapkan tiap entry berbentuk `{ card, orientation, position }` langsung (`orientation` di top level, bukan nested di `entry.orientation`). `interpretCard()` yang dipanggil di dalamnya pun melempar error karena `orientation` selalu `undefined`, dan Result Page jatuh ke empty state alih-alih menampilkan hasil. Lolos dari `node --check` (murni masalah shape data saat runtime, bukan syntax) dan baru ketahuan dari `test_phase6_flow.mjs` (`jsdom`, mensimulasikan flow sungguhan sampai render Result Page) — bukan dari unit test `interpretation.js` sendiri (yang benar semua karena dites dengan shape data yang sudah benar). Diperbaiki dengan me-map `entries` ke shape yang benar sebelum dikirim ke `synthesizeReading()`. Pelajaran yang diambil: unit test modul murni tidak cukup untuk menangkap mismatch kontrak antar-modul — perlu ada minimal satu integration test yang benar-benar memanggil page controller end-to-end.
