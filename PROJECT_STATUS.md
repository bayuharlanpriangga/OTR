### Phase 14 — Cloud Sync (Roadmap Phase 14 / Master Spec §36-46)
**Goal Roadmap**: "Menghubungkan seluruh application state dengan Supabase" untuk Reading/History/Journal/Favorites/Profile/Settings, dengan Supabase sebagai source of truth untuk authenticated users dan localStorage turun jadi cache/guest storage/temporary state.

**Dua celah spec yang ditemukan & ditutup sesi ini** (lihat `supabase/migrations/0003_phase14_cloud_sync.sql` untuk detail lengkap tiap keputusan):
1. **Kolom `category` hilang dari `readings`** — ada di record reading lokal sejak Phase 7 (dipakai badge kategori di History/Result), tapi tidak pernah ada di `CREATE TABLE readings` manapun (§41 maupun `0001_init_schema.sql`). Ditambah lewat `alter table ... add column if not exists` (nullable, tidak mem-backfill baris lama).
2. **`user_settings` akhirnya dibuat** — Phase 12 (lihat entri di bawah, baris "Sengaja tidak dibuat") sengaja menundanya karena §36 menyebutnya tapi tidak pernah memberi schema-nya, dan belum ada fitur yang membutuhkannya. Sekarang Settings benar-benar perlu disinkronkan, jadi schema-nya ditentukan sendiri di migration Phase 14: satu baris per user (`user_id` sebagai primary key, bukan uuid terpisah), `reduced_motion boolean` — mengikuti persis bentuk objek settings lokal (`STORAGE_KEYS.SETTINGS`, `js/core/storage.js`) yang sudah ditetapkan Phase 8.

**4 service baru (`js/services/`), pola "dual backend" konsisten**: tiap fungsi publik cek `state.user` SEKALI per panggilan (bukan flag statis) — ada user → Supabase, tidak ada → fallback ke fungsi `core/storage.js` yang SAMA PERSIS dipakai sebelum Phase 14 (jalur guest tidak berubah perilaku sama sekali).
- **`reading-service.js`** — `listReadings/getReadingById/saveReading/deleteReading/setReadingFavorite`. Bentuk record yang dikembalikan SAMA untuk kedua backend. `saveReading()` (cloud): insert `readings` lalu `reading_cards` (posisi slug lokal → `position_id` uuid lewat query `spread_positions` + `position_index`, pola resolve yang sama dengan `migration-service.js` Phase 13); kalau insert `reading_cards` gagal, baris `readings` yang telanjur dibuat dihapus lagi (best-effort cleanup, sama semangat dengan "gagal = tidak ada jejak" di `migration-service.js`). `deleteReading()` (cloud) mengandalkan `on delete cascade` (`reading_cards`/`journals`) alih-alih replikasi manual seperti guest storage.
- **`journal-service.js`** — `listJournalEntries/getJournalByReadingId/saveJournalEntry/deleteJournalEntry`. "One reading = one journal" (§25) dipertahankan di cloud lewat upsert-by-`reading_id` manual (cek dulu ada/tidak, baru update/insert — bukan `supabase.upsert()`, karena unique constraint di schema cloud ada di `id`, bukan `reading_id`).
- **`settings-service.js`** — beda pola dari 2 di atas: localStorage SELALU jadi sumber first-paint (Phase 8, tidak berubah — `app.js` tidak pernah menunggu network untuk menerapkan `data-reduced-motion`). `syncFromCloud(userId)` ditambahkan sebagai langkah TERPISAH yang dipanggil sekali setelah sesi diketahui (`app.js` `restoreSession()`, `login.js`, `register.js`) dan lagi tiap buka `/settings`: cloud ada isinya → tarik ke cache lokal (device lain jadi konsisten); cloud belum ada baris (akun ini belum pernah punya baris `user_settings`) → baris cloud dibuat dengan `DEFAULT_SETTINGS` (**`reducedMotion:false`**, bukan cache lokal — lihat "Bugfix pasca-Phase 14" di bawah). `saveSettings(partial, user)` selalu menulis lokal dulu (instan), upsert ke cloud kalau ada user — kegagalan upsert cloud di-`console.warn` saja, TIDAK membatalkan perubahan lokal.

### Bugfix pasca-Phase 14 — isolasi Settings antar-akun (dilaporkan Orias)
**Gejala**: login ke akun A (device tertentu), lalu login ke akun B di device yang sama — Settings B ikut kebawa nilai A, padahal reading/journal A dan B sudah benar-benar terpisah (RLS + filter `user_id` sejak awal, itu sudah benar).

**Akar masalah**: `syncFromCloud()` versi awal, saat menemukan akun BELUM punya baris `user_settings` sama sekali, meng-upload cache lokal (localStorage) APA ADANYA sebagai settings awal akun itu — dengan asumsi keliru "belum ada baris cloud = login pertama kali dari device ini, jadi cache lokal pasti milik akun ini". Asumsi itu salah begitu SATU device dipakai gantian oleh lebih dari satu akun (skenario Orias): localStorage adalah state per-DEVICE/BROWSER, bukan per-akun — begitu akun A logout lalu akun B login di device yang sama, cache lokal MASIH berisi nilai A (logout tidak membersihkan cache Settings, sesuai desain "localStorage = cache" di Roadmap Phase 14), dan versi lama kode ini akan "memaksa" nilai itu jadi milik B juga.

**Perbaikan**: `syncFromCloud()` sekarang, kalau akun belum punya baris cloud, SELALU membuatnya dari `DEFAULT_SETTINGS` (`{ reducedMotion: false }`, sumber tunggal sama persis dengan `DEFAULT_SETTINGS` di `core/storage.js`) — tidak pernah dari cache lokal. Cache lokal ikut ditimpa ke default itu juga, supaya konsisten dengan apa yang baru ditulis ke cloud. Reading/journal/favorites TIDAK terpengaruh perbaikan ini (sudah benar sejak awal, selalu difilter `user_id` + RLS).

**Trade-off yang disadari & diterima**: user yang set Reduced Motion sebagai TAMU lalu langsung Daftar (`register.js`) tidak lagi otomatis membawa preferensi itu ke akun barunya — akun baru selalu mulai dari default, sama seperti akun manapun yang belum pernah menyentuh Settings. Ini BEDA dari Guest Migration reading/journal (`migration-service.js`, Phase 13) yang memang secara eksplisit "mengklaim" data tamu sebagai milik akun yang baru dibuat — bedanya, reading/journal adalah DATA yang jelas kepemilikannya begitu diklaim, sedangkan Settings adalah preferensi device yang ambigu (tidak ada cara membedakan "preferensi tamu ini sebelum daftar" dari "sisa sesi akun lain di device yang sama") — jadi untuk Settings, default aman dipilih di atas kenyamanan minor.

**Verifikasi**: `scripts/test_phase14_settings_isolation.mjs` (Node murni + mock `js/integrations/supabase.js` sementara, pola sama dengan runtime test Phase 13 — tidak ikut deliverable, `supabase.js` asli dikembalikan setelah test) — 10/10 assertion lulus: akun A sync pertama kali dapat default (bukan cache lokal yang kebetulan `true`); akun B (belum pernah sync) setelah "logout A / login B" di device yang sama TIDAK mewarisi `true` milik A, baris cloud B benar-benar dibuat dengan `false`; login ulang ke akun A setelah itu tetap dapat `true` miliknya sendiri (bukan default, bukan sisa B) — membuktikan isolasi berjalan DUA ARAH, bukan cuma "B tidak dapat A" tapi juga "A tidak ikut ke-reset gara-gara B".

- **`profile-service.js`** — plumbing minimal (`getProfile`/`updateProfile`) disiapkan sekarang, dipakai nanti Phase 18 (halaman Profile penuh) — pola yang sama dengan `auth-service.js` yang ditulis Phase 12 sebelum ada UI-nya di Phase 13. ## Important Decisions
- Router pakai hash (`#/...`), bukan History API — supaya kompatibel static hosting tanpa rewrite rule.
- Font: Fraunces (display) + Public Sans (body) + IBM Plex Mono (data/angka) via Google Fonts CDN.
- Palet warna "night-reading table": obsidian/plum sebagai ruang, gold sebagai foil-accent, oxblood untuk state reversed/destructive.
- Data Minor Arcana (56 kartu) di-generate dari kombinasi tema suit × tema rank/court, bukan ditulis satu-satu manual. Teks Major Arcana (22 kartu) ditulis individual.
- `tarot-keywords.js` sengaja dipisah dari `tarot-cards.js` supaya fitur search/filter (Phase 9) & quiz (Phase 21) bisa jalan tanpa nge-load seluruh teks upright/reversed 78 kartu.
- `image` path memakai format `/assets/images/tarot/{suit-or-major}/{slug}.webp` — placeholder, asetnya diisi di Phase 4.
- **Randomization pakai `crypto.getRandomValues()` dengan rejection sampling** (bukan modulo langsung) supaya distribusi shuffle/orientation tidak bias ke angka kecil — sesuai Master Spec §10. Fallback ke `Math.random()` hanya kalau Web Crypto API benar-benar tidak tersedia di environment.
- **`TarotEngine` sengaja dipisah dari `TarotDeck`**: `deck.js` cuma tahu soal kartu fisik (draw/shuffle/reset), tidak tahu apa itu "reading" atau "spread". `tarot-engine.js` yang mengorkestrasi deck + orientation + spread jadi satu reading entity. Pemisahan ini supaya tiap modul gampang dites sendiri-sendiri (lihat runtime test Phase 3).
- **Reveal dipisah jadi state tersendiri dari draw** (`drawing` → `revealing` → `interpreting`), bukan digabung jadi satu langkah — mengikuti state machine Master Spec §15 dan mencegah UI (Phase 5) "skip" langsung dari draw ke interpretasi tanpa render animasi reveal.
- **`drawCard()` mengembalikan objek kartu penuh** (`card`, hasil resolve dari `getCardById`), tapi yang disimpan permanen ke `reading.cards` hanya `{ positionId, cardId, orientation }` — konsisten dengan schema Reading Entity Master Spec §14 (tidak menyimpan data kartu yang sudah redundan dengan `data/tarot-cards.js`).
- **`js/components/tarot-card.js` sengaja tidak tahu apa-apa soal `TarotEngine`** — komponen cuma nerima props data kartu + flag state. Pemisahan ini konsisten dengan pola yang sudah dipakai di Phase 2 & 3 (data/logic independen dari UI): Phase 5 nanti yang jadi "lem" antara `engine.drawCard()` dan `renderTarotCard()`.
- **Reversed orientation memutar seluruh wajah kartu 180°** (bukan cuma teks atau cuma artwork) — meniru tampilan kartu tarot fisik yang benar-benar terbalik, bukan sekadar ikon "reversed" di kartu yang tetap tegak. Badge kecil di pojok (tidak ikut rotasi) yang menjaga keterbacaan status orientasi.
- **Background art kartu pakai CSS `background-image` di sebuah `<div>`, bukan `<img>`** — karena `image` path di `data/tarot-cards.js` masih placeholder (aset `.webp` belum ada, lihat Known Issues Phase 2/3). Dengan `background-image`, gambar yang gagal load tidak memunculkan broken-image icon; huruf awal nama kartu (`.tarot-card__art-fallback`) selalu jadi fallback yang terlihat sengaja, bukan rusak. Begitu aset asli tersedia, tidak perlu ubah komponen — tinggal isi file di path yang sudah direferensikan.
- **`js/pages/reading.js` sengaja membuat `TarotEngine` baru tiap kali `render()` dipanggil** (bukan singleton module-level yang dipertahankan lintas navigasi) — navigasi ke `#/reading` = mulai reading baru, konsisten dengan mental model "reading" sebagai sesi sekali jalan. State reading yang **sudah selesai** dipertahankan lewat `js/core/state.js` (bukan lewat instance engine), supaya Result Page bisa dibaca ulang tanpa bergantung ke module reading.js.
- **Kategori interpretasi (general/love/career/spiritual) dipilih di step Pertanyaan, bukan otomatis dari spread** — walau tiap spread punya `category` default (dipakai sebagai nilai awal `<select>`), user tetap bisa override. Diteruskan apa adanya ke `interpretCard()`/`synthesizeReading()` (Phase 6) sebagai parameter `category`.
- **(Supersedes catatan Phase 5)** Result Page sekarang benar-benar memakai `synthesizeReading()` untuk "Overall Theme/Key Message/Reflection" — bukan lagi ringkasan sementara. Disclaimer "Interpretation Engine penuh menyusul di Phase 6" sudah dihapus dari UI karena sudah tidak akurat.
- **"Simpan Reading" dan "Tulis Journal" di Result Page dibuat `disabled` dengan `title` yang menyebutkan fase aktivasinya** (Phase 8, Phase 11) — bukan disembunyikan begitu saja — supaya user tahu fitur itu memang direncanakan, bukan lupa dikerjakan.
- **Form Pertanyaan/Niat/Kategori dibaca lewat `FormData(form)`**, bukan `form.<name>.value` — lebih eksplisit, dan (efek samping yang disengaja dimanfaatkan) membuat halaman ini testable lewat `jsdom` tanpa workaround.
- **Prioritas makna Master Spec §22 diimplementasikan penuh 4 tier walau tier 1 ("position-specific") saat ini tidak pernah punya data untuk dipakai** — pilihan sadar, bukan disederhanakan jadi 3 tier. Alasannya: (a) tetap sesuai kontrak spec apa adanya, (b) jadi titik ekstensi nyata kalau suatu saat ada kebutuhan makna per-posisi yang authored (mis. **Bugfix (ditemukan lewat smoke test manual pertama di browser sungguhan, pasca-Phase 7): kartu tidak animasi flip sama sekali — langsung terbuka tanpa transisi.** Root cause di `js/components/tarot-card.js` (Phase 4), bukan CSS: `reveal()`/`hide()` men-set `data-revealed` lalu langsung memanggil `rerender()` (`container.innerHTML = tarotCardHTML(state)`), yang mengganti seluruh elemen kartu dengan elemen DOM baru yang *sudah* lahir dalam state akhirnya. Karena browser tidak pernah melihat perubahan atribut pada elemen yang sama di antara dua frame, CSS transition di `.tarot-card__inner` (`tarot-card.css`) tidak punya apa pun untuk di-animasikan — kartu langsung snap ke hasil akhir. Ini bug yang sudah ada sejak Phase 4/5 tapi lolos dari seluruh runtime test `jsdom` sebelumnya karena test-test itu cuma memverifikasi atribut akhir (`data-revealed === "true"`, dst), bukan memverifikasi identitas elemen DOM sebelum & sesudah — jsdom juga tidak mengeksekusi CSS transition sama sekali, jadi kelas bug ini secara struktural tidak mungkin ketahuan lewat `jsdom`, cuma lewat browser sungguhan.

Atribut `aria-hidden` di-toggle manual saat reveal/hide supaya screen reader tidak membaca teks "Terbalik" sebelum kartu benar-benar dibuka.
  - `setOrientation()`/`setDisabled()`/`update()` tetap memakai `rerender()` — aman karena ketiganya dipanggil di luar momen animasi flip (sebelum kartu di-reveal, atau mengganti kartu yang masih tertutup).
  - Ditambahkan `buildAriaLabel()` sebagai helper bersama, dipakai baik oleh `tarotCardHTML()` (di-escape untuk HTML) maupun `reveal()`/`hide()` (raw, lewat `setAttribute` yang tidak butuh escape) — supaya logic label tidak duplikat di dua tempat dan bisa saling konsisten.
  - Diverifikasi lewat `test_reveal_flip_fix.mjs` (`jsdom`, one-off, tidak ikut deliverable): 18/18 assertion, termasuk assertion inti "`handle.el` sebelum dan sesudah `reveal()` adalah elemen DOM yang sama (`===`)" — cek yang sebelumnya tidak pernah ditulis di test manapun dan yang seharusnya menangkap kelas bug ini kalau ada di masa depan.
